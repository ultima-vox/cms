# G0: удобство административного интерфейса

Источник: main `0a10ade2182c5ea7c8d246e9dbe81cfa10abae9c`, 19 октября 2026. Родитель: [#105](https://github.com/ultima-vox/cms/issues/105), epic [#102](https://github.com/ultima-vox/cms/issues/102). Это аудит текущих сценариев и предложение интерфейса. Предложения ниже ещё не реализованы и не означают приёмку G0.

## Главный вывод

Редактор должен работать со страницей и её содержимым как с одной задачей. Сейчас пользователь сначала создаёт узел структуры, затем самостоятельно находит документ, созданный владельцем типа страницы. Поверх этого интерфейс показывает технические коды, статусы и настройки, нужные разработчику. Исправление требует связности сценариев и понятных состояний, а не только новых цветов.

Сохранить работающие PHP-шаблоны, общий shell, навигацию модулей, папки, поиск/фильтры документов и серверную пагинацию. Не делать вторую административную панель или SPA. Не переносить Documents/Infosystem в Core ради общего экрана.

## Предлагаемая организация экрана

Общий shell: сайт и домен, короткая навигация зарегистрированных модулей, переход к разделам, профиль. Разделы управления контентом и технические настройки различимы; видимость определяется правами. Пункты будущих модулей не рисовать до их установки.

Экран страницы: breadcrumbs → название и публичный адрес → содержимое владельца типа → публикация и доступ. SEO и технические параметры доступны отдельно; не смешивать настройки маршрута с HTML. На первом шаге достаточно ссылки в редактор владельца и обратного перехода: встраивать чужие контроллеры или дублировать формы не требуется.

Экран списка: заголовок и основное действие → папки → поиск/фильтры → таблица → пагинация. Сохранять одинаковые положения действий. Подписи состояний должны объяснять, что реально видно посетителю: опубликованная версия может существовать одновременно с новым черновиком. Цвет не должен быть единственным различием.

Экран документа: название → редактор → сохранение/публикация с понятным текущим состоянием. История — дополнительная секция. Разработческий код и формат хранения не должны быть обязательными знаниями контент-менеджера.

Это предложения для проверки, а не утверждение, что пользовательские исследования уже выполнены. Тёмная тема, новый набор иконок и анимации не имеют приоритета перед этими сценариями.

## Воспроизводимые наблюдения браузера

Новый [browser_editor_baseline.cjs](../../tests/browser_editor_baseline.cjs) запускается после существующего MVP browser smoke в [MVP workflow](../../.github/workflows/mvp.yml). Прямой запуск допускается только на одноразовой loopback-установке, уже подготовленной `mvp_http_smoke.py` и `browser_mvp.cjs`:

```bash
MVP_EDITOR_BASELINE_DISPOSABLE=1 NODE_PATH=/tmp/cms-browser/node_modules node tests/browser_editor_baseline.cjs
```

Три сценария на 390/1024/1440, по одному прогону каждого:

1. Найти неопубликованный `Browser list` документ через фильтр, открыть его, вернуться ссылкой «К документам»; записать, сохранился ли query.
2. Изменить HTML одноразового документа и сохранить черновик, проверить сохранённое содержимое.
3. Создать дочернюю страницу типа `documents.page` со статусом `draft`, зафиксировать доступность прямой ссылки в редактор контента. На этом сценарий завершается: «страница создана» не равно «содержимое заполнено и опубликовано».

Артефакт CI `g0-editor-baseline`: `report.json` и screenshots списка, документа и созданной страницы на трёх ширинах. JSON содержит SHA, Node/Chromium, параметры, число явных click/fill/select действий, automation wall time и navigation timing, наблюдения за возвратом и DOM-эвристику доступных имён. Известные UX-дефекты записываются как наблюдения; ошибки создания/сохранения и JS прерывают проверку.

Замеры **не являются** временем работы человека, сравнением с HostCMS, серверным профилированием, p50/p95 или полной WCAG-проверкой. Снимки надо просмотреть при review; успешный запуск не доказывает удобство. Используется существующий MVP fixture из 26 документов, не заявленный в #105 Content 1k/10k. Данные одноразовые; повторный запуск требует чистой установки. Webroot функционально покрывается существующим HTTP journey, этот browser baseline запускается только для public layout/PG16.

## Границы приёмки G0-D и дальнейшая UX-проверка

Серверный Content 1k/10k baseline реализован отдельно: [методика и измерения](content-performance-baseline.md), [постоянный snapshot](baselines/content-v1-2026-10-19.json). Он не добавляет instrumentation в Core. Для G0-D совместно рассматриваются эти измерения и три автоматизированных browser flow выше; решение по этапу фиксируется в [release gates](release-gates.md).

Полные задачи с человеком — создание и публикация страницы с контентом; поиск/редактирование/возврат; работа с папкой и материалами — остаются G10/G-REL-07. Автоматизированные наблюдения покрывают лишь часть этих задач и не заменяют пользовательскую приёмку. Это требование полного релиза, а не дополнительный неоговорённый блокер G0.

В human review записывать начало/конец задачи, успешность, ошибки, возвраты и затруднения. Нового и опытного редактора оценивать отдельно; automation clicks не заменяют эти данные. Целевые сокращения шагов утверждаются после baseline. Не объявлять G0/G1 или production принятыми из-за добавления этого файла либо зелёного CI.
