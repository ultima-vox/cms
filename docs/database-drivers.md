# PostgreSQL и legacy MySQL/MariaDB

PostgreSQL 16+ — основной backend и выбор по умолчанию. Если `DB_DRIVER` отсутствует у существующей установки, используется `pgsql`; реквизиты и данные автоматически не меняются. MySQL 8.0.21+ / MariaDB 10.11+ — альтернативный режим legacy для совместимого хостинга, выбираемый явно при установке.

## Установка

1. В панели хостинга создайте отдельную пустую БД и пользователя, которому доступны только эта БД и её объекты. Для MySQL/MariaDB нужны InnoDB, utf8mb4, создание таблиц, индексов и триггеров; глобальные права администратора СУБД не требуются. Если провайдер не разрешает триггеры, legacy-установка не поддерживается.
2. Для PHP 8.4 включите `pdo_pgsql` либо `pdo_mysql` соответственно выбранной СУБД. Для остальной CMS нужны `dom`, `mbstring`, `json`; ZIP-обновления требуют `zip`.
3. Распакуйте webroot-дистрибутив в уже назначенный корень сайта. Менять домашнюю директорию не нужно. Приватный `app/` должен быть закрыт веб-сервером; см. `MVP.md`.
4. Откройте `/install`, выберите СУБД. PostgreSQL выбран заранее; MySQL/MariaDB подписан `legacy`. При смене стандартного варианта порт переключается 5432 ↔ 3306; введённый нестандартный порт сохраняется.
5. Установщик проверяет подключение, версию сервера и пустоту БД. В `.env` сохраняются `DB_DRIVER=pgsql` или `DB_DRIVER=mysql` и выбранные параметры. MariaDB использует PDO-драйвер `mysql`.

Для CLI/управляемого развёртывания пример legacy-конфигурации:

```dotenv
DB_DRIVER=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=cms
DB_USER=cms
DB_PASS=your-password
```

Это настройка новой установки, не команда конвертации работающей PostgreSQL-базы. Замена `DB_DRIVER` на существующем сайте не переносит таблицы, миграционную историю и содержимое. Между СУБД нужен отдельный проверенный экспорт/импорт; такого мигратора пока нет.

## Общие сценарии и различия

Общие: сайты/домены, явный доступ пользователей, папки, макеты и их иерархия, структура, документы и версии, ИС/группы/элементы, поиск и типизированные JSON-фильтры, авторизация, метаданные модулей, штатное онлайн-обновление. SQL принадлежит репозиториям владельца; Core предоставляет небольшие фрагменты диалекта и блокировки, не ORM и не переписчик произвольного SQL.

| Механизм | PostgreSQL | Legacy MySQL/MariaDB |
| --- | --- | --- |
| JSON | JSONB, поддержка GIN в существующей схеме | JSON и JSON_CONTAINS; типы значений сохраняются, GIN не эмулируется |
| Миграции | Существующие SQL-файлы и их контрольные суммы сохраняются | Отдельные SQL в `migrations/mysql/`, актуальная начальная схема вместо воспроизведения PostgreSQL-истории |
| Транзакционные блокировки | advisory xact lock | InnoDB-строки `runtime_locks`; освобождаются при завершении транзакции |
| Блокировка установки/миграций | session advisory lock | GET_LOCK/RELEASE_LOCK в пределах текущей БД |
| Ограничения сайтов/папок | FK, индексы, триггеры | Составные FK, вычисляемые ключи частичной уникальности, триггеры дерева |
| Очистка данных удалённого модуля (`purge`) | Существующий транзакционный механизм | Заблокирована до изменения файлов. Отключение/удаление пакета с сохранением данных доступны |

Производительность сравнивается на одинаковом объёме данных и сценарии. MySQL/MariaDB не объявляются равными JSONB/GIN по индексированию; нагруженные JSON-фильтры потребуют предметных индексов и измерений внутри владельца данных.

## Миграции и онлайн-обновление legacy

DDL в MySQL/MariaDB может неявно завершать транзакцию; общий `ROLLBACK` не отменяет весь набор изменений схемы. Поэтому PostgreSQL-механизм не используется для имитации атомарности legacy.

- Перед SQL-миграцией legacy-runner записывает и фиксирует `dirty=TRUE` и checksum. После успешного выполнения снимает флаг. Незавершённая миграция блокирует автоматический повтор. Не сбрасывайте `dirty` вручную без проверки фактической схемы и данных.
- Онлайн-обновлятор блокирует запросы и получает общую блокировку БД, затем создаёт приватный потоковый снимок таблиц, данных и триггеров. `mysqldump`, SSH и отдельные процессы на хостинге не нужны.
- Снимок ограничен 256 MiB в сериализованном виде. Нужны свободное место и время PHP для снимка и возможного восстановления. Превышение лимита останавливает обновление до замены файлов. Эта копия не заменяет внешнее резервное копирование.
- Поддерживается отдельная БД CMS только с InnoDB-таблицами и стандартными SQL-идентификаторами. Произвольные представления, сторонние движки и процедуры не включены в гарантируемый снимок. Процедуры/функции/события должны отсутствовать: проверка выполняется до замены файлов.
- До завершения миграций сайт остаётся в обслуживании. При ошибке восстанавливаются БД и код; если восстановление не удалось или результат COMMIT неизвестен, обслуживание сохраняется.
- Успешный COMMIT отмечается уникальным токеном в БД. Standalone recovery получает ту же session-блокировку, проверяет токен и либо сохраняет новый код, либо восстанавливает проверенный снимок и старые файлы. Отсутствие токена нельзя проверять параллельно ещё работающей транзакции.
- При прерывании возьмите имя `backup-...` из журнала и выполните `php bin/update-recover.php backup-YYYYMMDD-HHMMSS-xxxxxxxx`. Если SSH недоступен, эту CLI-команду должен запустить провайдер/администратор через панель. Веб-доступа к снимку и неавторизованного URL восстановления нет.

Незавершённая первичная установка в MySQL может оставить объекты из уже выполненного DDL. Установщик не очищает такую БД автоматически: сохраните диагностику, устраните причину и используйте новую пустую БД либо восстановите согласованную копию.

## Контракт стороннего модуля

Модуль с SQL-миграциями должен поставлять собственный `migrations/mysql/` для legacy. При отсутствии runner отказывает, а не применяет PostgreSQL SQL к другой СУБД. Имена и checksum исторических миграций не меняются. MySQL DDL не выполняется внутри транзакции приложения. Доменные различия JSON-запросов остаются в модуле.

## Проверки

CI: PostgreSQL 16 (существующий полный набор), MySQL 8.0 и 8.4, MariaDB 10.11 и 11.4. Для legacy выполняются начальная схема, повтор миграций, метаданные, репозитории, изоляция папок/сайтов, SQL-сбой и восстановление обновления; отдельная HTTP-проверка устанавливает webroot-пакет с нуля и проходит редакторский сценарий. Само наличие списка версий не заменяет зелёный результат соответствующих jobs.

Официальные пояснения различий:

- MySQL implicit commit: https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html
- MySQL atomic DDL не означает transactional DDL: https://dev.mysql.com/doc/refman/8.0/en/atomic-ddl.html
- MariaDB JSON: https://mariadb.com/docs/server/reference/data-types/string-data-types/json
