# Модуль обновлений CMS

«Обновления» → «Проверить обновления» → список изменений → «Обновить». Проверка сохраняется для установки на 24 часа; кнопка привязана к версии и SHA-256 просмотренного релиза. Перед загрузкой сервер повторно проверяет релиз. Фоновая установка не выполняется.

## Штатное подключение

`updater` использует обычные `module.json`, `ModuleInterface`, автозагрузчик и Extension API. Права, меню и маршруты регистрируются провайдером. В дистрибутив модуль включён по умолчанию. В «Модули» доступны штатные синхронизация, отключение и включение. Отключённый модуль не регистрирует меню и маршруты; ранняя защита незавершённого deployment продолжает работать.

Отдельный `updater-module.zip` выпускается вместе с каждым релизом; внутри стандартный пакет с `module.json` в корне, без ядра, конфигурации и зависимостей Composer. Установка в сборку **без updater**: «Модули» → загрузка пакета → синхронизация → включение `updater` → синхронизация прав. Требуется Core ≥0.3.0 (поддержка внешней транзакции миграций и ранней защиты deployment). Загруженный пакет по правилам CMS устанавливается выключенным. Не загружайте ZIP поверх уже встроенного updater: встроенные модули обновляются вместе с поставкой CMS; для установленных из ZIP действуют стандартные update/remove и политика подписей пакетов.

При переходе с прежней обновлялки 1.0.0 после установки релиза один раз нажмите «Модули» → «Синхронизировать». Это добавит новые права. В следующих обновлениях модуль синхронизирует метаданные автоматически.

- `updates.view`: просмотр, проверка релизов и история.
- `updates.apply`: установка (дополнительно требуется `updates.view`).

`updates.view` получают superadmin и admin. `updates.apply` получает только доверенный superadmin: установка кода является глобальным действием. Редактор их не получает. Состояние проверки и история хранятся в приватном `storage/updates`, а не в сессии пользователя. Новых таблиц ядра модуль не создаёт.

## Установка и миграции

Нужны PHP 8.4, PHP zip, исходящий HTTPS с OpenSSL/allow_url_fopen, права записи в поставку и место для распакованного релиза и резервной копии. Страница показывает предварительную готовность сервера. Проверки точных путей, локальных изменений и контрольных сумм выполняются до замены файлов.

Канал — публичные релизы `ultima-vox/cms`. Workflow публикует релиз после успешного CI и проверки обеих раскладок (`public`, `webroot`). Проверяются сертификат HTTPS, хосты перенаправлений, SHA-256 архива и каждого файла. Сторонний URL в интерфейсе не вводится. Доверие основано на официальном репозитории и TLS; отдельной цифровой подписи релиза пока нет.

Обновляются только файлы поставки. `.env`, `storage`, данные пользователей и неизвестные поставке файлы сохраняются. Изменённые вручную файлы поставки блокируют установку. Удаляются только исчезнувшие из релиза ранее отслеживаемые файлы. В `webroot` обновляются также публичные копии assets и входного файла.

Добавленные SQL-миграции ядра и **включённых** модулей выполняют штатные `MigrationRunner` и `ModuleMigrationCoordinator`, с их порядком зависимостей и контрольными суммами. Изменение или удаление старой SQL-миграции запрещено. Новые миграции выключенных модулей остаются неприменёнными. После миграций обновляются версии модулей и ставится задание штатной синхронизации. Права и провайдеры сверяются `ModuleManager::sync()` в первом свежем PHP-запросе после замены: старый процесс содержит прежние классы и Composer map. Задание защищено PostgreSQL advisory lock; при ошибке остаётся в очереди и запрос завершается ошибкой, а не работает с частично зарегистрированными правами.

Все миграции и синхронизация входят в одну внешнюю транзакцию PostgreSQL. Исполнители используют savepoint для каждой миграции и удерживают advisory locks до завершения внешней транзакции. Обычный CLI сохраняет прежнее поведение самостоятельных транзакций. SQL миграций должен быть транзакционным: без явных COMMIT/ROLLBACK, CREATE DATABASE, VACUUM, CREATE INDEX CONCURRENTLY и внешних побочных эффектов.

Во время замены ранний `DeploymentGuard`, независимый от Composer и БД, блокирует все новые PHP-запросы ответом 503. Активные запросы не позволяют начать замену — повторите попытку. Установщик освобождает собственную shared lease и получает exclusive lock. Проверка применяется также к адресу установки; исключений по URL нет.

## Ошибки, история и восстановление

Резервные копии заменённых файлов и журнал находятся в `storage/updates/backup-*`. Страница показывает последние 20 операций: версии, время, результат и имя копии. При обычной ошибке миграции транзакция откатывается, файлы восстанавливаются, обслуживание снимается. Ошибка кеша или аудита **после успешной установки** выводит отдельное предупреждение и не выдаётся за откат релиза.

При аварийном завершении процесса маркер обслуживания остаётся. В журнале записан полный xid8 транзакции. Через терминал владельца сайта выполните:

```sh
cd /путь/к/приложению
php bin/update-recover.php backup-YYYYMMDD-HHMMSS-xxxxxxxx
```

Имя берётся из `storage/updates/maintenance.json`; для webroot путь приложения заканчивается на `app/`. Скрипт работает только с активной незавершённой операцией. Для транзакционной установки подключается к БД с существующей конфигурацией и проверяет `pg_xact_status`: `committed` — оставляет новый код и завершает обслуживание, `aborted` — восстанавливает старые файлы. При неизвестном результате или недоступной БД обслуживание сохраняется: скрипт не угадывает результат COMMIT. У очень старых транзакций PostgreSQL может уже не хранить статус; такое восстановление требует ручной проверки. Старые операции без транзакции восстанавливаются по файловому журналу.

После восстановления перезапустите PHP-обработчик через FASTPANEL. Восстановление прерванной установки не является произвольным откатом успешно установленной версии: обратные SQL-миграции не выполняются. Копии не удаляются автоматически; удаляйте старые после проверки сайта. Файловая копия не заменяет резервное копирование всей БД.

## Масштабирование

Модуль предназначен для одной установки с общим файловым деревом. Несколько независимых серверов обновляются централизованным deployment-процессом с общими миграциями; ядро не хранит распределённое состояние обновлений. OPcache должен разрешать invalidate/reset или проверять timestamps; иначе нужен перезапуск PHP-обработчика. Изменять nginx для модуля не требуется.

После появления миграций существующую CMS обновляйте через модуль обновлений. Полный установочный ZIP предназначен для новой установки; замена файлов вручную без применения SQL не является корректным обновлением установленной БД.
