# Онлайн-обновления для разработки

После однократной загрузки стартового пакета: «Обновления» → «Проверить обновления» → прочитать изменения → «Обновить». Нужны права `modules.manage`, PHP zip, исходящий HTTPS и запись PHP в файлы поставки. Работающий сайт на время замены кода отвечает 503; активные PHP-запросы блокируют начало замены, повторите попытку спустя несколько секунд.

Канал использует публичные релизы `ultima-vox/cms`. Workflow публикует релиз только после успешных обычного CI и двух проверок установки. Проверяется HTTPS с сертификатом, разрешённые хосты перенаправлений, SHA-256 архива и каждого файла; сторонний URL в интерфейсе задать нельзя. В этой версии доверие основано на официальном GitHub-репозитории и HTTPS; отдельной цифровой подписи релизов нет.

Сохраняются `.env`, весь `storage/`, пользовательские макеты в `storage/templates/` и файлы, не входившие в предыдущую поставку. Изменённые вручную файлы поставки блокируют обновление. Для `webroot` синхронно обновляются приватная копия и публичные assets. `.env`, установка БД и пользовательские данные в обновление не входят. Обновление схемы БД блокируется по списку и контрольным суммам SQL; автоматические миграции — отдельный последующий этап.

Резервные копии заменённых файлов и журнал находятся в `storage/updates/backup-*`. При обычной ошибке записи выполняется обратное восстановление. При аварийном завершении процесса маркер обслуживания сохраняется, дальнейшая раздача PHP блокируется. Для восстановления после такой аварии через терминал владельца сайта:

```sh
cd /путь/к/приложению
php bin/update-recover.php backup-YYYYMMDD-HHMMSS-xxxxxxxx
```

Подставьте имя резервной копии из `storage/updates/maintenance.json`; используйте PHP 8.4. Для webroot путь приложения заканчивается на `app/`. После восстановления перезапустите PHP-обработчик сайта через панель. БД восстановление не затрагивает. Резервные копии не удаляются автоматически: следите за свободным местом и удаляйте старые после проверки обновлённого сайта.

Обновлялка предназначена для одной установки с общим файловым деревом. Несколько независимых серверов обновляются централизованным deployment-процессом; механизм обновлений не вводит распределённое состояние в ядро. OPcache должен допускать `opcache_invalidate`/`opcache_reset` или проверять timestamps; при принудительно отключённой проверке и запрещённом сбросе обновление требует перезапуска обработчика.
