# MVP на PHP-хостинге

Цель версии: через браузер установить CMS, войти в админку, создать страницу, опубликовать текст и проверить изменения на публичном сайте. Это проверка реального PHP/PostgreSQL приложения, не макет интерфейса.

## Установка

1. Создайте отдельный тестовый поддомен и отдельную **пустую** PostgreSQL-базу. Требуются PHP 8.4+, PostgreSQL 16+, расширения `pdo_pgsql`, `dom`, `mbstring`, `json`. Настройте HTTPS. До окончания установки ограничьте доступ к поддомену средствами хостинга.
2. Распакуйте `ultima-vox-cms-mvp.zip` в отдельный каталог. Архив уже содержит `vendor`; Composer и SSH на хостинге для установки не нужны.
3. Корень сайта в панели хостинга должен указывать **на `public/` внутри этого каталога**, а не на весь каталог CMS. Приватные файлы, `.env`, `storage` и `vendor` не должны раздаваться веб-сервером. Для Apache нужен mod_rewrite и разрешённый `.htaccess`; для Nginx используйте `deploy/nginx.conf.example` с вашими путями и PHP-FPM.
4. На время установки разрешите PHP запись в корень каталога приложения и `storage/`. Не создавайте `.env` заранее: установщик запишет его сам. Если хостинг не позволяет назначить `public/` корнем сайта, не загружайте весь проект в публичный каталог — сначала нужна отдельная схема размещения.
5. Откройте `/install`: проверка окружения → параметры PostgreSQL → название, полный URL, email и пароль администратора. URL — адрес поддомена без подпапки. Пароль администратора: 12–72 байта.
6. После установки откройте `/admin/login`. Главная страница уже создана и опубликована; её документ изначально пустой. Пароль администратора в архиве отсутствует — вы задаёте его сами.
7. После успешной установки уберите право PHP изменять код и корень проекта. Сохраните запись в `storage/cache`, `storage/logs`, `storage/templates`; `.env` оставьте доступным только владельцу PHP-процесса. Снимите временное ограничение доступа, если нужно показать MVP коллегам.

Установщик не переустанавливает заполненные базы и не удаляет данные. Миграции применяются последовательно: если установка прервана на миграции, не очищайте общую базу и не повторяйте установку поверх неизвестного состояния. Для повторной проверки возьмите новую пустую базу. Если БД готова, а хостинг отказал в записи `.env`, требуется ручное восстановление конфигурации из ваших параметров БД.

## Что проверить за 10 минут

1. Войти в админку; открыть «Структура», «Документы», «Макеты», «Сайты» и «Модули».
2. В «Документах» изменить документ главной страницы (код `node-<id главной>`), сохранить с публикацией. Проверить `/` в отдельном приватном окне браузера.
3. В «Структуре» создать дочерний узел главной: название «Проверка», slug `poc`, тип «Документ», статус `published`, активность включена. Документ создаётся автоматически.
4. В «Документах» открыть новый документ, добавить текст и опубликовать. Проверить `/poc` без авторизации.
5. Сохранить другой текст как черновик: публичный текст не должен меняться. Опубликовать новую версию: публичный текст должен обновиться.
6. Проверить вёрстку админки на вашем экране и сообщить, где сценарий редактирования неудобен. Именно эти замечания определяют следующую итерацию MVP.

## Границы версии

Работают динамические страницы, Documents, Structure, макеты, авторизация и права, управление сайтами/доменами и установленными модулями. Обычные публичные адреса пока соответствуют `nodes.path`, например `/poc`. Настройка формата статической публикации не переключает эти адреса.

Статическая раздача, автоматическая регенерация, перенос канонических URL, редиректы и готовая эксплуатационная кластерная конфигурация не включены. CLI статики является дополнительным инструментом и не нужен для просмотра MVP.

Проверка MVP выполняется отдельным CI: свежая установка через HTTP, вход, создание страницы, публикация, анонимное чтение, черновик, повторная публикация и загрузка CSS. Это функциональная проверка; визуальную оценку на вашем реальном хостинге ещё нужно пройти.
