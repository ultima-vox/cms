# MVP на PHP-хостинге

Цель версии: через браузер установить CMS, войти в админку, создать страницу, опубликовать текст и проверить изменения на публичном сайте. Это реальное PHP-приложение. PostgreSQL — основной вариант по умолчанию; MySQL/MariaDB доступны явно как legacy (см. `database-drivers.md`).

## Без изменения корня сайта

Архив `ultima-vox-cms-mvp-webroot.zip` распакуйте прямо в пустую папку тестового поддомена, назначенную хостингом. Менять её назначение в панели не нужно. Снаружи находятся `index.php` и `assets/`, приложение — в `app/`. Composer и SSH не нужны.

Для Apache 2.4 нужны mod_rewrite и разрешённые директивы `.htaccess` (включая `Require` и `Options`). Загрузите оба скрытых файла `.htaccess`: в корне и в `app/`. Для Nginx администратор хостинга должен применить `app/deploy/nginx.webroot.conf.example`: он закрывает `/app` и передаёт запросы в корневой `index.php`. Nginx не читает `.htaccess`; без этих правил размещать этот архив нельзя. Назначенный корень сайта остаётся прежним.

Перед установкой проверьте, что `/app/composer.json` возвращает 403 или 404. На время установки разрешите PHP запись в `app/` и `app/storage/`, затем откройте `/install`. Требования к БД и действия установщика описаны ниже. Все указанные далее приватные пути для этого архива отсчитываются от `app/`. После установки также проверьте недоступность `/app/.env`.

## Установка с отдельным public/

1. Создайте отдельный тестовый поддомен и отдельную **пустую** базу. Требуются PHP 8.4+, PostgreSQL 16+ (`pdo_pgsql`) либо legacy MySQL 8.0.21+/MariaDB 10.11+ (`pdo_mysql`), а также `dom`, `mbstring`, `json`. Настройте HTTPS. До окончания установки ограничьте доступ к поддомену средствами хостинга, разрешив также исходящий IP самого сервера для проверки размещения. HTTP Basic Auth проверка не передаёт.
2. Распакуйте `ultima-vox-cms-mvp.zip` в отдельный каталог. Архив уже содержит `vendor`; Composer и SSH на хостинге для установки не нужны.
3. Корень сайта в панели хостинга должен указывать **на `public/` внутри этого каталога**, а не на весь каталог CMS. Приватные файлы, `.env`, `storage` и `vendor` не должны раздаваться веб-сервером. Для Apache нужен mod_rewrite и разрешённый `.htaccess`; для Nginx используйте `deploy/nginx.conf.example` с вашими путями и PHP-FPM.
4. На время установки разрешите PHP запись в корень каталога приложения и `storage/`. Не создавайте `.env` заранее: установщик запишет его сам. Если менять корень сайта неудобно, используйте вариант архива выше.
5. Откройте `/install`: проверка окружения → выбор СУБД и параметры подключения → название, полный URL, email и пароль администратора. URL — адрес поддомена без подпапки. Пароль администратора: 12–72 байта.
6. После установки откройте `/admin/login`. Главная страница уже создана и опубликована; её документ изначально пустой. Пароль администратора в архиве отсутствует — вы задаёте его сами.
7. После успешной установки уберите право PHP изменять код и корень проекта. Сохраните запись в `storage/cache`, `storage/logs`, `storage/templates`; `.env` оставьте доступным только владельцу PHP-процесса. Снимите временное ограничение доступа, если нужно показать MVP коллегам.

Установщик не переустанавливает заполненные базы и не удаляет данные. Миграции применяются последовательно: если установка прервана на миграции, не очищайте общую базу и не повторяйте установку поверх неизвестного состояния. Для повторной проверки возьмите новую пустую базу. Если БД готова, а хостинг отказал в записи `.env`, требуется ручное восстановление конфигурации из ваших параметров БД.

## Что проверить за 10 минут

1. Войти в админку; открыть «Структура», «Документы», «Макеты», «Сайты» и «Модули».
2. В «Документах» изменить документ главной страницы (код `node-<id главной>`), сохранить с публикацией. Проверить `/` в отдельном приватном окне браузера.
3. В «Структуре» создать дочерний узел главной: название «Проверка», slug `poc`, тип «Документ», статус `published`, активность включена. Документ создаётся автоматически.
4. В «Документах» открыть новый документ, добавить текст и опубликовать. Проверить `/poc` без авторизации.
5. Сохранить другой текст как черновик: публичный текст не должен меняться. Опубликовать новую версию: публичный текст должен обновиться.
6. Проверить вёрстку админки на вашем экране и сообщить, где сценарий редактирования неудобен. Именно эти замечания определяют следующую итерацию MVP.

## Границы версии

Работают динамические страницы, Documents, Structure, макеты, авторизация и права, управление сайтами/доменами и установленными модулями. Обычные публичные адреса пока соответствуют `nodes.path`, например `/poc`. Настройка формата статической публикации не переключает эти адреса.

Статическая раздача, автоматическая регенерация, перенос канонических URL, редиректы и готовая эксплуатационная кластерная конфигурация не включены. CLI статики является дополнительным инструментом и не нужен для просмотра MVP.

Проверка MVP выполняется отдельным CI: свежая установка через HTTP, вход, создание страницы, публикация, анонимное чтение, черновик, повторная публикация и загрузка CSS. Это функциональная проверка; визуальную оценку на вашем реальном хостинге ещё нужно пройти.

## Проверка настоящего Apache

CI содержит `apache-hosting` для обеих раскладок ZIP: Apache 2.4 с PHP 8.4, mod_rewrite и AllowOverride All. Приватные статические файлы и публичные ресурсы проверяются до и после установки, весь HTTP-сценарий редактора проходит через Apache, а не встроенный PHP-сервер. Отрицательная webroot-конфигурация с AllowOverride None обязана обнаруживать утечку приватного файла и проваливать проверку защиты.

Это стенд CI, Docker не требуется владельцу сайта. Тест Apache не доказывает безопасность произвольного nginx/FASTPANEL и не заменяет проверку конфигурации конкретного хостинга. Установщик проверяет защиту перед изменением БД (см. ниже). Полная матрица nginx/reverse-proxy/HTTPS остаётся отдельной задачей P0.

## Проверка защиты перед установкой

До создания таблиц установщик запрашивает временный файл в `assets` через указанный URL и проверяет приватные пути (в webroot: `/app/composer.json`, `/app/.env.example`, `/app/public/index.php`). Приватные пути должны вернуть 403/404; иной ответ, ошибка сети, несовпадение контрольного файла или redirect останавливают установку. Контрольный файл удаляется и при ошибке. БД, `.env` и администратор ещё не создаются.

На время установки PHP нужны запись в публичный `assets` и исходящие HTTP(S), включая доступ сервера к своему публичному домену. Для HTTPS требуется действительный сертификат и доверенная цепочка CA. Укажите конечный адрес после перенаправлений. Проверка обращается только по фиксированным путям, не отправляет cookies/пароли и не следует перенаправлениям. DNS-адрес фиксируется для всех запросов; домены пока требуют IPv4 A-запись, IPv6 поддерживается как буквальный адрес. После установки доступ на запись к коду/публичным ресурсам можно убрать.

Внутренние, loopback и служебные IP по умолчанию запрещены. Для изолированного LAN-стенда владелец сервера может **до запуска PHP** явно задать единственный точный origin, например `INSTALLER_LOCAL_ORIGIN=http://127.0.0.1:8086`. Это разрешает сетевое обращение только к выбранному адресу; проверка контрольного файла и защиты остаётся обязательной. Не формируйте значение из Host или пользовательского ввода. В обычной публичной установке параметр не нужен; в CI он задаётся процессу тестового сервера, в `.env` дистрибутива не добавляется.

Если хостинг запрещает обращение к собственному домену или имеет единственный PHP worker и переписывает проверяемые запросы обратно в PHP, проверка может завершиться таймаутом и остановит установку. Обхода проверки из формы нет. Нужно исправить маршрутизацию/доступность с провайдером; безопасная обработка private статическими правилами web-сервера остаётся обязательной. Это точечная проверка размещения, а не полный аудит всех alias, location и файлов хостинга.
